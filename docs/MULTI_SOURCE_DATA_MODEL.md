# Multi-source business data model

RumiReach treats each source as an independent contributor of observations, not as an unquestioned truth provider.

## Core rules

1. A business profile may contain observations from multiple admitted sources.
2. Every observed field value records its source, source URL, collection time, and (when available) source dataset timestamp.
3. Values from different sources are not silently overwritten.
4. Multiple distinct values for the same field are surfaced as a conflict for human review.
5. Missing values remain unknown; they are not inferred from another field.
6. A source is only admitted after its access method, reuse terms, attribution, and rate limits are reviewed.
7. "Publicly visible" does not automatically mean "permitted to collect or reuse".

## Current implementation

The SQLite `field_observations` table stores:

- `candidate_id`: current candidate record the observation belongs to
- `source_id`: registered source identifier
- `field_name` and `field_value`: individual observed value
- `source_url`: page or object where the value was observed
- `observed_at`: when RumiReach collected it
- `source_timestamp`: upstream dataset timestamp, if supplied
- `verification_status`: currently `unverified` for imported OSM values
- `confidence`: nullable; left empty until a defensible scoring method exists

The OSM adapter writes field observations for name, category, address, phone, website, and email. It does not mark those fields as verified.

API:
- `GET /api/candidates/:id/provenance` returns the candidate, its field observations, and any conflicting values.

## Planned source adapters

| Source | Planned role | Admission gate |
|---|---|---|
| OpenStreetMap regional extract | Broad POI discovery and baseline attributes | ODbL attribution/share-alike review and extract provenance |
| Overpass | Small, bounded incremental discovery | Shared-service limits, sequential requests, backoff |
| Business-owned website | Enrich contact and service fields | Respect robots, site terms, access controls, and low request rates |
| Government/open datasets | Regional or sector-specific enrichment | Confirm publisher, license, update date, and reuse rights |
| User-provided CSV | Import records supplied by the operator | Record import batch and original file/source; validate fields |

No adapter should be activated merely because a scraper library exists. Scrapy, Playwright, and similar projects are extraction frameworks; they do not grant access rights or provide a business database.

## Matching and conflict handling

The current implementation attaches observations to a candidate generated by the OSM adapter. Cross-source entity resolution is not implemented yet. The next matching layer must use explainable evidence (for example, normalized phone, website domain, and geographic proximity), retain match reasons, and route ambiguous matches to review. It must not merge businesses solely because their names look similar.

## Data quality

RumiReach should report, per region and source:
- number of records and unique source objects
- field completeness
- conflicting field values
- age of latest observation and upstream dataset timestamp
- rejected, failed, and partial source jobs

Do not present a single "verified" badge or a freshness claim without showing which fields and sources support it.
